### High

#### H-1. `Game.changeScene` (formerly `Game.goTo`) drops queued A → B → A transitions and synchronous `onActivate` self-restarts

1. **File & lines**: `packages/web/src/game.ts:390-405` and `packages/web/src/game.ts:563-623` (baseline)
2. **Description**: `Game` tracked in-flight and queued scene transitions in a `pendingScenes: Map<SceneId, Promise<void>>` whose entries were only removed in `.finally()` after the entire transition chain settled.
3. **Trigger / reproduction**:
   - **Case 1 (A → B → A queue)**: While scene `"b"` is preparing asynchronously, the caller queues `game.changeScene("b")`, then `game.changeScene("c")`, and then `game.changeScene("b")` again before `"b"`'s first promise settles. Because `"b"` is still present in `pendingScenes`, the second `game.changeScene("b")` returns the first `"b"` promise instead of queuing a transition back to `"b"` after `"c"`. When the queue finishes, the game remains stuck on `"c"`.
   - **Case 2 (`onActivate` self-restart)**: A scene's `onActivate` callback synchronously invokes `void game.changeScene(sameId)` to restart the scene. Because `engine.activate(scene)` runs inside `navigate` before `.finally()` deletes `sameId` from `pendingScenes`, the call returns the currently finishing transition promise and silently drops the restart.
4. **Impact scope**: Asynchronous scene navigation in `@simpludify/web` (`Game.changeScene`).
5. **Recommended fix**: Replace `pendingScenes: Map<SceneId, Promise<void>>` with a single `pendingScene?: { id: SceneId; task: Promise<void> }` representing only the latest pending target at the tail of the navigation queue, and clear it immediately before `this.engine.activate(scene)` (as well as in `.finally()` if still pointing to the current task).
6. **Status**: **Fixed** in `packages/web/src/game.ts` and verified in `tests/browser/architecture.spec.ts`.

#### H-2. `PixiRenderer` fails to reconcile replaced `TilemapLayer` / `GeometryTilemapLayer` instances or coexist both on the same `Actor`

1. **File & lines**: `packages/web/src/renderer.ts:442` and `packages/web/src/renderer.ts:532-558` (baseline)
2. **Description**: `PixiRenderer` stored both `TilemapVisual` and `GeometryTilemapVisual` in a single `private readonly tilemaps = new Map<Actor, TilemapVisual | GeometryTilemapVisual>()` keyed by `Actor`, and during `prepare()` checked only whether `actor.get(TilemapLayer.type)` or `actor.get(GeometryTilemapLayer.type)` was truthy.
3. **Trigger / reproduction**:
   - Removing a `TilemapLayer` (or `GeometryTilemapLayer`) from an `Actor` and adding a new `TilemapLayer` with a different `Tilemap` on the same `Actor` kept the old `TilemapVisual` rendering the stale `Tilemap`.
   - Attaching both a `TilemapLayer` and a `GeometryTilemapLayer` to the same `Actor` caused `this.tilemaps.has(actor)` to be `true` after creating `TilemapVisual`, completely skipping `GeometryTilemapVisual` creation.
4. **Impact scope**: Tilemap and GeometryTilemap rendering in `@simpludify/web` (`PixiRenderer`).
5. **Recommended fix**: Separate `tilemaps: Map<Actor, TilemapVisual>` and `geometryTilemaps: Map<Actor, GeometryTilemapVisual>`, and verify `!layer.disposed && layer.map === entry.map` during reconciliation before reusing an existing visual.
6. **Status**: **Fixed** in `packages/web/src/renderer.ts` and verified in `tests/browser/architecture.spec.ts`.

### Medium

#### M-1. Duplicate button indices in `GamepadBindings` cause false self-conflicts and duplicate entries on `addBindings`

1. **File & lines**: `packages/core/src/interaction/gamepad-bindings.ts:89-91` and `packages/core/src/interaction/action-bindings.ts:177-189` (baseline)
2. **Description**: While `keys`, `mouse`, and gamepad axis `negative`/`positive` lists deduplicated controls on construction and patch editing, `checkedGamepadBindings` did not deduplicate `buttons` by button index, and `editGamepad` deduplicated using `JSON.stringify(v)` rather than the physical button index `control(v)`.
3. **Trigger / reproduction**:
   - Constructing `new ActionBindings({ Jump: { gamepad: { buttons: [0, 0] } } })` or calling `addBindings("Jump", { gamepad: { buttons: [{ button: 0, threshold: 0.7 }] } })` when button `0` is already bound leaves two entries for button `0` in `Jump.gamepad.buttons`.
   - Calling `controller.conflicts("gamepad")` then iterates over `Jump.gamepad.buttons`, sees button `0` twice on `Jump`, and reports a false conflict `{ control: { kind: "gamepad-button", button: 0 }, actions: ["Jump"] }` with a single action.
4. **Impact scope**: `GamepadBindings`, `ActionBindings`, and `ActionController.conflicts("gamepad")` in `@simpludify/core`.
5. **Recommended fix**: Deduplicate `buttons` by physical button index (`typeof entry === "number" ? entry : entry.button`) in both `checkedGamepadBindings` and `editGamepad`, keeping the latest entry/threshold.
6. **Status**: **Fixed** in `packages/core/src/interaction/gamepad-bindings.ts` and `packages/core/src/interaction/action-bindings.ts`; regression tests added in `tests/unit/input-bindings.test.ts`.

#### M-2. `CanvasVisual` wheel handler divides by zero when the host element has zero width or height

1. **File & lines**: `packages/web/src/canvas-visual.ts:234-252` (baseline)
2. **Description**: Unlike the pointer listener in `CanvasVisual.native` (which guards `if (rect.width <= 0 || rect.height <= 0) return;`), the `wheel` listener divided `(event.clientX - rect.left) / rect.width` and `(event.clientY - rect.top) / rect.height` without checking `rect.width` and `rect.height`.
3. **Trigger / reproduction**: Dispatching a `wheel` event on the host element while its bounding client rect has `width === 0` or `height === 0` (e.g., `display: none` or collapsed layout container) passes `NaN` coordinates into `root.wheel(...)`, throwing an uncaught `EngineError("INVALID_UI", "Canvas UI values must be finite")` in the browser event listener.
4. **Impact scope**: `CanvasVisual` wheel input handling in `@simpludify/web`.
5. **Recommended fix**: Add `if (rect.width <= 0 || rect.height <= 0) return;` in the `wheel` listener before computing logical coordinates.
6. **Status**: **Fixed** in `packages/web/src/canvas-visual.ts` and verified in `tests/browser/canvas-ui.spec.ts`.

#### M-3. `Game.scene(id, setup)` lacks upfront validation of `id` and `setup`

1. **File & lines**: `packages/web/src/game.ts:340-343` (baseline)
2. **Description**: `game.scene(id, setup)` stored `(id, setup)` in `this.scenes` without validating that `id` is a non-empty string or that `setup` is a function. Invalid values only failed later when navigating to the scene (or threw a raw `TypeError: setup is not a function`).
3. **Trigger / reproduction**: Calling `game.scene("", fn)` or `game.scene("play", null as unknown as SceneSetup)` succeeded at registration time instead of throwing `EngineError("INVALID_VALUE", ...)`.
4. **Impact scope**: `Game.scene` registration in `@simpludify/web`.
5. **Recommended fix**: Validate `typeof id === "string" && id.length > 0` and `typeof setup === "function"` in `Game.scene()`, throwing `EngineError("INVALID_VALUE", ...)` immediately.
6. **Status**: **Fixed** in `packages/web/src/game.ts` and verified in `tests/browser/architecture.spec.ts`.

#### M-4. External consumer CI fixture (`oz-coden/Run-To-Exit`) pins a commit calling `game.goTo("puzzle")`

1. **File & lines**: `.github/workflows/ci.yml:303` (`ref: e3c6f50ad837e2d2c598a1a1d01c47077b33d00c`, `tests/e2e/game.spec.ts:395` in `oz-coden/Run-To-Exit`)
2. **Description**: The `sdk-consumer-build` job in `.github/workflows/ci.yml` checks out `oz-coden/Run-To-Exit` at `e3c6f50ad837e2d2c598a1a1d01c47077b33d00c`, installs the candidate `@simpludify/core` and `@simpludify/web` tarballs, and runs `npm run check` (`tsc --noEmit`). In that pinned external commit, `tests/e2e/game.spec.ts:395` calls `await game.goTo("puzzle")`.
3. **Trigger / reproduction**: Because `game.goTo()` was removed without a compatibility alias as required for v0.1.7, running `npm run check` inside the pinned `Run-To-Exit` checkout fails with `TS2339: Property 'goTo' does not exist on type 'Game'`.
4. **Impact scope**: External consumer CI job (`sdk-consumer-build` and downstream `sdk-consumer-e2e`) in `.github/workflows/ci.yml`.
5. **Recommended fix**: As documented in `docs/work-reports/2026-11-09-ci-sdk-candidates.md` ("Run To Exit stays pinned for reproducibility, so an intentional API break can require updating the fixture and its pinned source before integration"), update `tests/e2e/game.spec.ts:395` in `oz-coden/Run-To-Exit` from `game.goTo("puzzle")` to `game.changeScene("puzzle")` and advance the pinned `ref` in `.github/workflows/ci.yml` when integrating `review/v0.1.7-quality` into `main`.
6. **Status**: **Unfixed in Simpludify branch (requires external repository commit before `main` integration)**; verified locally that updating that single call in `Run-To-Exit` makes `npm run check`, `npm test` (35 unit tests), and `npm run build` pass against the candidate SDK tarballs.

### Low

#### L-1. `Tilemap.worldToTile(-0, -0)` returns `-0` instead of `+0`

1. **File & lines**: `packages/core/src/game/tilemap.ts:338-344` (baseline)
2. **Description**: `Math.floor((-0 - 0) / tileWidth)` evaluates to `-0` in JavaScript. Unlike `TileGeometry` (which normalizes `-0` via `clean()`), `Tilemap.worldToTile(-0, -0)` returned `{ x: -0, y: -0 }`, failing `Object.is(p.x, 0)` checks.
3. **Trigger / reproduction**: Calling `map.worldToTile(-0, -0)` on a `Tilemap` at origin `(0, 0)`.
4. **Impact scope**: `Tilemap.worldToTile` in `@simpludify/core`.
5. **Recommended fix**: Normalize `tx` and `ty` with `|| 0` before passing to `tilePoint(tx, ty)`.
6. **Status**: **Fixed** in `packages/core/src/game/tilemap.ts`; unit test added in `tests/unit/tilemap.test.ts`.

#### L-2. `SharedImages` retains failed URLs if all waiters abort before the underlying browser decode settles (Observation / Design note)

1. **File & lines**: `packages/web/src/renderer.ts:138-193`
2. **Description**: `SharedImages.acquire` aborts only the caller's waiter promise when its `AbortSignal` fires while keeping the underlying `HTMLImageElement` decode running in case another consumer requests the same URL. If all waiters abort and the image load finishes, `cleanup` disposes the unreferenced entry immediately (`entry.refs === 0`).
3. **Trigger / reproduction**: Verified that `cleanup` properly deletes the entry and destroys the `ImageSource` when `entry.refs === 0` after load or error completion.
4. **Impact scope**: Internal `SharedImages` lifecycle in `@simpludify/web`.
5. **Recommended fix**: No change required for v0.1.7; when the dedicated Assets system is introduced in v0.2.0, explicit preload/cache eviction policies should supersede ad-hoc per-renderable `SharedImages` retention.
6. **Status**: **Verified safe / Deferred to v0.2.0 Assets design**.

## 3. API rename: `game.goTo()` → `game.changeScene()`

In accordance with the v0.1.7 API specification:

- Renamed `Game.prototype.goTo(id: SceneId): Promise<void>` to `Game.prototype.changeScene(id: SceneId): Promise<void>` in `packages/web/src/game.ts`.
- Removed `goTo` completely with no compatibility alias and no `@deprecated` wrapper.
- Preserved the return type (`Promise<void>`) and asynchronous scene preparation, cancellation, and error rollback semantics.
- Updated all 13 examples (`examples/*/main.ts`), the Vite starter template (`templates/npm-vite/main.ts`), benchmark and site live-check scripts (`scripts/*.mjs`), package and type fixtures (`tests/package-fixture/main.ts`, `tests/types/canvas-ui.ts`), all 24 browser test files (`tests/browser/*.ts`), and all active English and Japanese documentation (`docs/en/**`, `docs/ja/**`). ## 6. Design considerations for v0.2.0

1. **Assets management boundary (`@simpludify/core` vs `@simpludify/web`)**:
   - Currently, `SpriteSheet` and `Renderable` hold declarative string URLs in `@simpludify/core`, while `SharedImages` in `@simpludify/web` lazily loads and reference-counts `HTMLImageElement` instances during `PixiRenderer.prepare()`.
   - For v0.2.0 Assets management, keep asset descriptors/handles host-independent in `@simpludify/core` while keeping network fetch, decoding, `AbortSignal` cancellation, and GPU texture upload strictly in `@simpludify/web`. Ensure scene-scoped asset bundles release deterministically when a `Scene` is deactivated or disposed during preparation.
2. **Scene transition re-entrancy & lifecycle hooks**:
   - `Engine.activate(scene)` is synchronous in Core, whereas `Game.changeScene(id)` is asynchronous in Web. Calling `void game.changeScene(...)` inside `scene.onActivate` or `scene.onDeactivate` queues a subsequent asynchronous transition after the current activation commits. Documenting this distinction clearly will prevent users from expecting synchronous scene replacement inside `onActivate`.
3. **Coordinated external consumer updates on breaking API changes**:
   - Because `.github/workflows/ci.yml` pins `oz-coden/Run-To-Exit` by commit SHA (`e3c6f50ad837e2d2c598a1a1d01c47077b33d00c`) and runs `npm run check` against the candidate SDK tarballs, any intentional breaking API rename (such as `game.goTo` → `game.changeScene`) requires updating `Run-To-Exit` and bumping the pinned SHA in `.github/workflows/ci.yml` prior to merging into `main`.
