## Confirmed findings and fixes

### Finding 1 — `AssetHandle.reload()` during background fallback retry ignores reload options and falsely resolves when the retry fails

- **Severity**: High
- **Target file & lines**: `packages/web/src/assets.ts:577-608, 754`
- **Root cause**:
  When an initial `scope.load({ kind, url, retry })` failed its first attempt and committed a fallback (`entry.asset = fallbackAsset`, `entry.status = "fallback"`), `handle.ready` resolved while `entry.task` remained active in the background waiting for `retry.once` or `retry.network`. If the caller invoked `handle.reload(options)` during that background retry:
  1. `AssetStore.start()` returned `entry.task` at line 582 before calling `settings(options)` at line 584, silently ignoring invalid `options` (such as `{ timeoutMs: 0 }`) and failing to preempt a stalled `retry.once.until` wait or trigger a `cache: "reload"` fetch.
  2. Because `entry.task` had been started with `reload = false`, when all retries in `entry.task` failed, `AssetStore.load()` checked `if (reload || !entry.asset) throw failure;` (line 754). Since `reload` was `false` and `entry.asset` held the fallback resource, `entry.task` resolved to `undefined` instead of rejecting, causing `await handle.reload()` to falsely resolve on a failed reload.
- **Reproduction condition**:
  Load an image or audio asset with `retry: { once: { until: pendingPromise } }` whose initial load fails and falls back, then call `await handle.reload({ timeoutMs: 0 })` or `await handle.reload()` while the retry is still pending and the reload attempt also fails.
- **Impact scope**:
  Callers awaiting `handle.reload()` on an asset in `"fallback"` state with background retries could neither validate `reload` options, preempt a hung `until` signal, nor detect that `reload()` failed.
- **Fix**:
  Validate `settings(options)` before checking `entry.task` in `AssetStore.start()`. When `reload && entry.asset` is true while an existing `entry.task` is running, abort `entry.controller` and start the new reload task (`reload = true`), guarding task cleanup with `if (entry.task === task)`.
- **Added test**:
  `tests/unit/assets.test.ts` — `"preempts a pending background retry on reload, validates reload options and rejects when reload fails on fallback"`
- **Verification**:
  Failed before fix (timed out waiting for `stalled.promise` and ignored `{ timeoutMs: 0 }`); passed after fix.
- **Commit SHA**: `66795e2` (`66795e277f9482e5c1f63875620c1bb5275498b8`)

### Finding 2 — `TilemapVisual` retains destroyed Pixi `Texture` references on live `Sprite`s after a managed atlas reload

- **Severity**: High
- **Target file & lines**: `packages/web/src/tilemap-visual.ts:63-70, 88-106` and `packages/web/src/assets.ts:627-629`
- **Root cause**:
  In `AssetStore.commit()`, `entry.listeners` are notified synchronously right before `this.release(old)` destroys the previous `ImageResource` (`texture.destroy(true)` and all cropped frame `Texture`s). Unlike `PixiRenderer` (which immediately assigns `sprite.texture = texture` inside its `resource.onChange` callback), `TilemapVisual`'s `lease.onChange` listener cleared `this.textures`, set `this.invalid = true`, and called `this.sync()`, which populated `this.textures` with new frame textures but did not update `sprite.texture` on existing `Sprite` instances in `this.sprites` until the next `TilemapVisual.render()` pass. When `this.release(old)` ran on the next line, every `Sprite` in `this.sprites` was left referencing a destroyed `Texture` (`texture.destroyed === true`, `texture.source === null`), and remained in that state indefinitely whenever the `Tilemap` was hidden (`map.visible = false` or actor disabled) or between `reload()` completion and the next frame.
- **Reproduction condition**:
  Place a `Tilemap` using a managed image atlas (`atlas.source.url`), render once so cell `Sprite`s are created, hide the tilemap (`map.visible = false`), and call `await atlas.reload()`.
- **Impact scope**:
  `TilemapVisual.sprites` held destroyed Pixi `Texture` instances after managed atlas recovery or reload whenever `TilemapVisual.render()` did not immediately rebuild visible cells.
- **Fix**:
  In `TilemapVisual.sync()`, after refreshing `this.textures`, iterate over existing entries in `this.sprites` and update `sprite.texture` to the new `Texture` (or remove the sprite if the cell became `null`) before `AssetStore.commit()` releases the old `ImageResource`.
- **Added test**:
  `tests/browser/assets.spec.ts` — `"replaces live tilemap sprite textures immediately on managed atlas reload even while hidden"`
- **Verification**:
  Verified in Chromium (desktop and narrow viewports).
- **Commit SHA**: `66795e2` (`66795e277f9482e5c1f63875620c1bb5275498b8`)

### Finding 3 — `Logger` consecutive deduplication merges distinct `DOMException`s and `Error` subclasses with prototype getters

- **Severity**: Medium
- **Target file & lines**: `packages/core/src/foundation/logger.ts:71-90`
- **Root cause**:
  `signature(entry)` encoded `Error` instances using `Object.getOwnPropertyDescriptors(value)` for fields and `Object.getOwnPropertyDescriptor(prototype, "name")?.value` on the immediate prototype only. Standard web/runtime exceptions such as `DOMException` define `name`, `message`, and `code` as prototype getters on `DOMException.prototype` rather than own data properties on the instance, and custom `Error` subclasses may inherit `name` from a deeper prototype. Consequently, `Object.getOwnPropertyDescriptors(domException)` returned `{}` and `signature()` produced the identical key `["error", "DOMException", []]` for two `DOMException`s with completely different `name` and `message` values, causing the standard Console sink to suppress the second fault as a duplicate.
- **Reproduction condition**:
  Report two consecutive errors whose `name` and `message` are provided by prototype getters (such as two distinct `DOMException` instances) through `logger.report()`.
- **Impact scope**:
  Consecutive distinct browser/host exceptions (`DOMException`, ` AudioContext` / `FontFace` / `AbortSignal` host errors) logged through `Logger` with `deduplicate !== false` were falsely deduplicated in the standard sink.
- **Fix**:
  In `signature()` (`packages/core/src/foundation/logger.ts`), walk the prototype chain for `Error` instances to resolve `name` (falling back to `value.name`) and include `["message", encode(value.message, depth + 1)]` when `message` is not already an own data property in `fields`.
- **Added test**:
  `tests/unit/logger.test.ts` — `"distinguishes errors whose name or message is inherited from a prototype getter"`
- **Verification**:
  Failed before fix (`output` had length 1 instead of 2); passed after fix.
- **Commit SHA**: `7c0f5ed` (`7c0f5ed9ee170140a3673977b7da77e9d9cb8fc3`)

### Finding 4 — Asset load timeout reports raw `DOMException` instead of `EngineError("ASSET_TIMEOUT")` during fallback commit

- **Severity**: Medium
- **Target file & lines**: `packages/web/src/assets.ts:700-745`
- **Root cause**:
  When `deadline` (`AbortSignal.timeout(policy.timeoutMs)`) aborted an in-flight `adapter.load()`, the `catch (cause)` block inside `AssetStore.load()` assigned `entry.error = cause` (the raw `TimeoutError` `DOMException`) and emitted the `ASSET_FALLBACK` warning before exiting the retry loop, only wrapping `failure` into `new EngineError("ASSET_TIMEOUT", "Asset load deadline expired", {}, { cause: failure })` at lines 733–739 after `fallback()` had already resolved `handle.ready` and notified `handle.onChange` listeners.
- **Reproduction condition**:
  Load an asset with a fallback (`image`, `audio`, or `font`) and a short `timeoutMs`, and inspect `handle.error` inside `handle.onChange` or immediately upon `await handle.ready`, or inspect the `ASSET_FALLBACK` diagnostic's `cause`.
- **Impact scope**:
  `handle.error` at `await handle.ready` / `onChange` and the `ASSET_FALLBACK` diagnostic `cause` exposed a raw `DOMException` instead of the documented `ASSET_TIMEOUT` `EngineError`.
- **Fix**:
  Normalize `cause` to `new EngineError("ASSET_TIMEOUT", "Asset load deadline expired", {}, { cause })` as soon as `deadline.aborted` is observed in the `catch` block before setting `entry.error`, running `fallback()`, or emitting `ASSET_FALLBACK`.
- **Added test**:
  `tests/unit/assets.test.ts` — `"normalizes timeout failures to ASSET_TIMEOUT before fallback notification"`
- **Verification**:
  Failed before fix (`observed[0]` was raw `TimeoutError` `DOMException`); passed after fix.
- **Commit SHA**: `66795e2` (`66795e277f9482e5c1f63875620c1bb5275498b8`)

### Finding 5 — `AudioPlayback` with a zero-duration `AudioBuffer` and `loop: true` computes `position = NaN` (`0 % 0`)

- **Severity**: Medium
- **Target file & lines**: `packages/web/src/audio.ts:183-194`
- **Root cause**:
  In `AudioPlayback.startIfReady()`, when `buffer.duration <= 0` (e.g. a zero-length decoded buffer) and `this.looping` is `true`, `this.position >= buffer.duration` (`0 >= 0`) evaluated to `true` and `this.position %= buffer.duration` computed `0 % 0 = NaN`. Passing `NaN` to `source.start(0, this.position)` throws a `TypeError` in Web Audio, transitioning the playback to `"failed"` and emitting an unexpected runtime audio error instead of finishing cleanly as `"ended"`.
- **Reproduction condition**:
  Play an audio asset whose decoded `AudioBuffer` has `duration === 0` with `{ loop: true }` on a running `AudioContext`.
- **Impact scope**:
  Looping playback of zero-duration audio buffers failed with an unhandled `NaN` offset error rather than completing cleanly.
- **Fix**:
  Guard `if (buffer.duration <= 0) { this.finish("ended"); return; }` in `AudioPlayback.startIfReady()` before computing the modulo offset or creating Web Audio nodes.
- **Added test**:
  `tests/unit/audio.test.ts` — `"handles zero-duration audio buffers and non-running context pauses without NaN offsets or leaked nodes"`
- **Verification**:
  Failed before fix; passed after fix.
- **Commit SHA**: `02deea3` (`02deea348244260006e145547cc9ba8bc6be147b`)

### Finding 6 — `Game.setFont()` does not trigger a render when called or when an in-flight font handle resolves or reloads

- **Severity**: Low
- **Target file & lines**: `packages/web/src/game.ts:404-420`
- **Root cause**:
  In `Game.setFont(asset)`, the `update` callback updated `--s-font` on `this.element.style` when `setFont()` was called or when `next.onChange(update)` fired, but did not guard `if (this.dead) return;` or invoke `if (this.ready) this.render();`. Under a custom/manual `FrameDriver` or between animation frames, `CanvasVisual` (which reads `--s-font` during `updateProjection()` / `render()`) kept its stale font family and layout metrics until another operation triggered `render()`.
- **Reproduction condition**:
  Call `game.setFont()` or pass a pending `AssetHandle<"font">` to `game.setFont(face)` after `await game.run()` with a manual `FrameDriver`, and inspect the rendered `CanvasVisual` text style after `await face.ready`.
- **Impact scope**:
  `CanvasUI` text style and metrics did not immediately reflect `game.setFont()` or asynchronous font completion/reload until the next frame tick.
- **Fix**:
  In `Game.setFont()`, guard `if (this.dead) return;` and call `if (this.ready) this.render();` inside `update()`.
- **Added test**:
  `tests/browser/media.spec.ts` — extended `"registers a real FontFace, switches the Game default and removes the final registration"` to verify immediate Canvas UI restoration on `game.setFont()` and asynchronous application when `game.setFont(late)` is called before `await late.ready` under a manual `FrameDriver`.
- **Verification**:
  Verified in Chromium (desktop and narrow viewports).
- **Commit SHA**: `02deea3` (`02deea348244260006e145547cc9ba8bc6be147b`)

## Reviewed areas with no defects found

- **Core / Web architectural boundary**: `packages/core` has zero imports outside itself and compiles cleanly without DOM, Node, or Pixi ambient types (`tests/unit/core-boundary.test.ts`, `npm run check`).
- **Scene retention & lifecycle invariants**:
  - `Engine.activate(scene, { previous: "retain" })` properly freezes actors, simulation tweens, presentation tweens, timers, and `ActionController` input while the scene is `Inactive`, while allowing owned resource registration (`Scene.assertAlive()` permits `Inactive` when `retained === true`).
  - `Game.navigate` and `Game.present` preserve the active scene and retained scene session when a retained scene's `renderer.prepare()` fails on reactivation (`tests/browser/scene-retention.spec.ts`).
  - If an `onActivate` callback disposes the newly activated scene, `Game.present` throws `SCENE_DISPOSED`, reports a fatal `engine.presentation` diagnostic, and disposes the `Game` and all retained scenes.
- **Audio hierarchy & voice replacement**:
  - `AudioGroup` prevents cycle creation because `game.audio.group(name, options)` only sets `parent` on initial creation and rejects reconfiguring existing groups with `AUDIO_GROUP_EXISTS`.
  - `maxVoices` replacement (`"replaced"`) accurately counts pending, playing, and paused voices across both per-asset limits and ancestor group limits, and `started` / `paused` voices pin their initial `AudioBuffer` generation across `asset.reload()`.
- **FontFace registration lifetime**:
  - Each `registerFont` call registers a unique `SimpludifyFont<N>` instance in `document.fonts` after `FontFace.load()` and `signal.throwIfAborted()`, and deletes that exact `FontFace` instance when the `AssetResource` is released after all scope handles, `game.setFont` leases, and idle cache entries are released.
- **Public API backward compatibility**:
  - No public method signatures, types, or error codes were broken or removed; all fixes preserve existing v0.2.0 public contracts while tightening edge-case behavior.

### Independent reproduction and follow-up fixes

- **Reload and retry.** Running the original regression test on the merge base reproduced the ignored invalid options. The review implementation also let a second owner abort an active explicit reload and could still falsely resolve a reload requested before the first fallback. Explicit reloads now replace ordinary loads and their retries, while concurrent reload callers share the active explicit operation after option validation. Releasing one owner cancels only its wait. A superseded task cannot finalize the replacement or report a stale failure after reentrant fallback notification. Tests cover shared ownership, a late result released exactly once and reload started inside an observer.
- **Tilemap atlas lifetime.** Existing Sprite textures are rebound synchronously on generation changes. The scan stays off the ordinary dirty-cell update path. A tile edit in a public asset callback can introduce an invalid frame after prevalidation. The visual releases sprites whose new frame cannot be resolved, retaining no references to textures about to be destroyed. Browser coverage exercises both renderers with hidden and disabled layers, removal and reinsertion, reentrant edits, recovery and final disposal.
- **Logger signatures.** The merge base suppressed distinct inherited errors. The original review change could invoke user getters, ignore a shadowing accessor in favor of a deeper data property, and serialize a raw inherited name. Signature generation now uses descriptors and the existing complexity limits. Accessor-backed host errors and cyclic values are incomparable and remain visible to the sink without invoking user getters. Plain comparable errors retain consecutive deduplication.
- **Timeout errors.** The merge base delivered a raw timeout cause to fallback observers. Normalization now also covers a deadline that expires while a custom fallback is in flight. The built-in fallback observers and its warning receive the same `ASSET_TIMEOUT` before notification, preserving the underlying cause. A late custom fallback is released.
- **Zero-duration audio.** The merge-base regression left a looping voice unfinished in the mock after starting at an invalid offset. The guard exits through the standard completion path without creating nodes. The reviewed test also exercises suspension, pause, resume and a subsequent playable buffer.
- **Canvas font updates.** Immediate and asynchronous font updates preserve the DOM and Canvas behavior under a manual frame driver. A render guard prevents recursive rendering. A font replacement releases its previous lease even when rendering throws. Browser coverage verifies both cases alongside the existing FontFace registration and cleanup checks.
