# 実装状況と開発ロードマップ

Simpludifyは、コード主導・2D特化の実験的なTypeScript製ゲームエンジンです。この文書では、**実装済みの機能・今後優先する機能・意図的に対象外とする機能**を明確に区別します。優先度は開発方針であり、公開日や将来のAPI名の確約ではありません。API、性能バジェット、移行手順、プラットフォーム対応は、個別の詳細設計とゲーム実装による検証を経て確定します。

## 製品方針・実装上の原則

- **コードを中心としたゲーム制作**を優先します。ゲーム側でロジックとUIを定義し、入力、描画、ライフサイクル、Host固有の処理をエンジンが扱います。標準的な用途でGUIエディタ、手書きのHTML、プラットフォーム別の実装を強制しません。
- **CoreとHostの責務を分離**し、CoreのHost非依存性を維持します。音声、描画、ファイルI/O、ネットワーク、配布パッケージなどの環境依存処理は明示的なアダプターで扱い、明確なリソース所有権を持たせます。プロセス間の毎フレーム通信など不必要な処理は避けます。
- 既存のAction、Scene、Actor/Component、Canvas UI、Tilemap、CollisionWorldの契約を活用し、同じ責務を持つ別系統のフレームワークを増やしません。破壊的変更には必ず移行計画を用意します。
- **小さく安定した構成要素**、適切な初期設定、文書化された拡張口を重視します。大規模なサブシステムは、実際のゲーム実装、テスト、測定された制約に基づいて段階的に導入します。
- 重い物理演算、ネットワーク、デスクトップ・モバイルHostなどは、可能な限り**任意導入の独立モジュール**として提供します。基本ランタイムへ必須依存させず、軽量性を保ちます。
- 各マイルストーンにはAPI文書、所有権とエラー処理の定義、代表的なHeadless/ブラウザテスト、破棄テスト、既知の制約が必要です。実験的な動作確認と正式なプラットフォーム対応を混同しません。

### 直近の実行順序（案）

以下は優先度表を実際の作業へ落とした段階的な計画です。**バージョン番号への固定割当やリリース日の約束ではありません。** 実装・公開はテストと実際のゲームでの検証後に判断します。

1. **品質基盤の改善：** 現行のWindows/Linux、パッケージ利用側、ブラウザ、公開サイトの検証を維持しつつ、Playwrightの依存インストール時間と公開後テストの不安定さを計測・改善します。失敗を無条件の再実行で隠さず原因を特定します。
2. **v0.2.0候補のAudio・Assetsをゲームで検証：** 効果音、BGM、ロード画面、Sceneをまたぐリソースの所有権を実例で確認します。
3. **Save / Load、Scene保持、Canvas UIの組み合わせ：** セーブと復元、ポーズ・再開、設定や確認ダイアログを具体的なゲームで検証します。
4. **デスクトップ配布の試作：** 同一のWebゲームからElectronとTauriを比較し、まず小さなデスクトップ成果物の起動・終了を検証します。正式サポートや自動配布は試作結果に基づいて段階的に決めます。
5. **外部利用の検証：** 初見の開発者が公開npmパッケージとガイドだけでサンプルを作成できるか確認し、必要に応じて作品紹介の任意投稿先を用意します。ユーザーの同意なくテレメトリーを組み込みません。

Audio/Assetsを優先しつつ、CI改善・導入体験の検証・デスクトップ試作の調査は並行して進められます。Particle、Camera、Networkingなどの既存候補は引き続き維持し、実際のゲームから得た制約に応じて順序を再評価します。

### CI・SDK利用側検証

通常CIは現行ソースからCore/Webの候補を一組生成し、独立したnpmプロジェクトで検証します。LinuxとWindowsではパッケージの内容、公開型、ビルド、Viteスターターを確認します。固定したRun To Exitは候補で一度ビルドし、デスクトップ・320 px・390 pxの各画面幅でWebGLとCanvas2DのPlaywright試験を実行します。配布するスターターには公開版SDKのlockfileを同梱します。

[公開レジストリ検証](npm-publishing.md)では対象バージョンを個別に検証します。検証範囲・所要時間・npm取得数の推計と限界は[作業報告](../work-reports/2026-11-09-ci-sdk-candidates.md)に記録しています。

### 高優先度の作業領域

#### Audio・Assets管理

- v0.2.0候補のバッファ再生、カテゴリ音量、明示ロードをゲームで検証します。ストリーミング、フェード、manifestはゲーム側の要件に合わせて検討します。
- アプリ全体とSceneのどちらがリソースを所有するかを明示し、シーンの重複稼働、読み込み失敗、中断、繰り返し利用、破棄を検証します。無制限の暗黙キャッシュは避けます。

#### 持続的ゲーム状態（Save / Load）

- ゲーム側が保存対象と復元方法を明示する、バージョン付き保存形式を基本とします。あらゆるComponentの自動シリアライズや任意ステップ途中からの完全復元は約束しません。
- 論理状態のシリアライズと、ブラウザ・デスクトップ・モバイルでの保存先を分離します。破損データ、スキーマ検証、移行、書き込みのアトミック性を設計します。
- **Replayは同一条件から入力を再現する仕組みであり、Save / Loadではありません。** 複数Sceneと設定・Assetsを含む実例で保存・読み込みを検証します。

#### Scene保持・オーバーレイ・モーダルUI

- Scene保持を土台に、ダイアログ等のオーバーレイ表示を検討します。
- 入力フォーカス、更新と描画の停止、非同期準備中の動作、所有権と破棄の整合性を慎重に設計します。
- Canvas UIプリミティブ上にモーダル／ダイアログコンポーネントを構築し、決定／キャンセル結果、キーボード・コントローラー操作、フォーカス復元、入れ子オーバーレイをサポートします。
- ロードマップに記載されているAPI名は提案であり、実装済みexportではありません。サンプルのゲーム実装で検証してから凍結します。

#### パーティクル・カメラ・ゲームプレイ制御

- パーティクルは一般的なプリセットと設定可能なエミッターから開始し、エミッターごとの予算とライフサイクル連動の破棄を持たせます。重いシミュレーションパーティクルと軽量な視覚効果を区別します。
- カメラ追従、画面揺れ、トランジションを拡張した上で、必要に応じて複数Viewportを検討します。ワールド／スクリーン変換と各ViewportのUI／入力境界をテストします。
- アクター、敵、メニュー用の任意の階層型状態機械モジュールを探索します。明示的な遷移ガードとクリーンアップをサポートし、実際の敵ウェーブサンプルで実証します。

#### 任意機能としてのネットワーク

- **Stage 1:** 明示的なトランスポート／セッションインターフェース、型付きメッセージ、切断／エラー処理。アプリケーション定義のサーバー基盤はエンジンの外側に置きます。
- **Stage 2:** 単一の同期モデルを前提とせず、実際のマルチプレイヤーユースケースを検証して状態複製、RPC、権威モデル、補間戦略を選定します。
- **Stage 3:** シミュレーション決定論、リプレイ互換性、ネットワーク制約が許容される証拠が得られた場合にのみ、予測とロールバックを検討します。固定ステップやReplayの存在がロールバックの安全性を自動保証するわけではありません。
- セキュリティ境界、ユーザー識別子、Host要件を文書化します。Coreは完全にオフラインで利用可能であり続けなければなりません。

### プラットフォームと物理の拡張

- **物理演算：** シンプルなゲームには現行の軽量Collider/CollisionWorldを維持します。力、Joint、CCDが必要なゲームに対してのみ、個別にインストール可能な外部剛体ライブラリを評価します。2つのソルバーを無秩序に混在させたり、矛盾する接触所有権を持たせることは避けます。ライブラリ選定の前に相互運用性と移行方法を定義します。
- **Electron / Tauri：** いずれか一方に偏ることなく両方を調査します。バンドルされたWebゲームコードのポータビリティを保ち、最小限のネイティブブリッジを使用し、不要な権限を拒否し、安全なコンテンツセキュリティポリシーを適用し、プロセスのクリーンな終了を検証します。同等の条件下でバンドルサイズ、実行時メモリ、起動時間をベンチマークします。
- **モバイル：** タッチ、ソフトキーボード／IME、ライフサイクルの一時停止、画面の向き、性能、ストア制約を考慮し、対応するHost／パッケージング作業と共にAndroidおよびiOSを調査します。Webビルドが動作することだけでは、ネイティブモバイル対応の認定にはなりません。

### 延期・検討対象外（Non-goals）

- **ビジュアルGUIエディタ：** アクティブなロードマップ項目ではありません。大幅な将来の進化と確固たる需要が実証された場合にのみ再検討します（10回以上のメジャー／マイナーリリース先になる可能性があります）。コード主導での制作が標準です。
- **組み込み3D：** 計画していません。エンジンは2Dに特化し続けます。
- **高度なキー設定：** キーコード、シーケンス、標準リバインドUI、高度なキャプチャは、Bindingセマンティクスが成熟するまで意図的に延期します。現行v0.1.6の物理Binding、単一入力キャプチャ、JSON設定は維持されます。
- **仮想化リスト：** 大規模リストの負荷が正当化された場合のみ設計候補とします。
- **完全なCSS/DOMパリティ、必須の汎用ECSリライト、独自GPUレンダラー、他言語SDK、汎用マルチプレイヤースタック：** 現在の製品方針では不要です。

### マイルストーン選定と受入基準

1. 具体的なゲームユースケースを持つ小さな垂直スライスを選択し、既存APIを尊重し、実装前にライフサイクルとエラーセマンティクスを文書化する。
2. Hostサービスから独立してCore契約を実装し、必要な箇所にのみ任意のプラットフォームアダプターを公開する。
3. 単体APIテストだけでなく、完全なゲームプレイシナリオを検証する。ブラウザテスト、ヘッドレステスト、破棄／再入テスト、エラーテストを含める。
4. ベンチマーク環境と制約を記録し、サポートブラウザ／デバイス／ターゲットのチェックリストを追加する。
5. 実証された結果に基づいてこのロードマップを更新する。実装と適切な検証の両方が揃うまで、計画機能を「実装済み」とマークしない。

## 実装済み機能

未公開のv0.2.0候補では、スコープ付きAsset、音声、FontFace、Scene保持、構造化診断を追加しています。[移行ガイド](migrate-0.2.0.md)を参照してください。

- **入力：** [物理Bindingと単一入力Capture](./specs/input-bindings.md)、キーボード・マウス・ゲームパッド設定、実行時リバインド、競合診断、JSON入出力。Core/Web v0.1.6はnpmで公開済みです（[公開記録](../work-reports/2026-11-05-v0.1.6-publication.md)）。
- **仮想入力：** [仮想スティック・ポインターコントロール](./specs/virtual-input.md)（固定・浮動・追従Axis2Dスティック、方向あり／なしのボタン、有効領域、Pointer所有権、既存ActionSourceとの合成）。
- **Tween：** [汎用数値Tween](./specs/tween.md)、Sceneのシミュレーション／表示クロック、寿命／チャネル所有権、シーケンス／パラレル、Actor描画およびCanvas/Sliderアダプター。
- **Canvas UI：** [Core側のUIツリーとFlex/テキスト/Pointerルーティング](./specs/canvas-ui.md)、フォーカス、[ネイティブ文字編集](./specs/text-input-design.md)、[標準コントロール](./specs/canvas-controls.md)（Checkbox/Slider/Select/TextInput/NumberInput）。[スクロール](./specs/scrolling.md)はドラッグ、慣性、重なったスクロール領域、スクロールバーに対応。
- **Grid・Tilemap：** [固定サイズGrid](./specs/grid.md)、[有限Tilemap](./specs/tilemap.md)、レイヤー、SpriteSheetフレーム、カリング、セル編集、[地形衝突](./specs/tilemap-collision.md)。
- **Sprite:** [SpriteSheetとSpriteAnimation](./specs/sprites.md)。グリッド・名前付き・矩形フレーム、画像共有、Actor単位の再生。
- **幾何タイル:** [三角形・六角形タイル](./specs/tile-geometry.md)。多角形タイルの単色描画、座標変換、選択、隣接セル判定。
- **ゲーム基盤：** DOM非依存Engine、Sceneライフサイクル、Actor/Component、Transform/Renderable/Motion/ActionMovement、Character、型付きイベント、シミュレーションタイマー、Seed付き乱数、Snapshot。
- **描画・Camera：** Pixiの図形・画像描画、描画順・透明度・表示制御、単一Camera/Viewport、World/Screen座標変換、CameraFollow、画像の非同期ロードとリース。
- **衝突：** [円・回転矩形のTrigger/Solid](collision.md)、レイヤー/マスク、Enter/Stay/Exit、CollisionBodyによる質量比に基づく位置補正。
- **シーン遷移：** [Sceneライフサイクル](scenes-ui.md)、非同期準備、リクエストのキュー・統合、準備失敗時の旧シーン保持、破棄中のキャンセル。
- **再現性：** [Random、Replay、固定ステップ](./specs/replay.md)。初期条件からAction列を再生できます。
- **サンプル：** Character、UI/Scene、Beacon Field、Signal Run、Blockfall、Prism Raid、Sprite Garden、Tile Trail、幾何タイル、Canvas UI、仮想入力、入力Bindingなど。
- **開発・配布：** dev/check/test/build/doctor CLI、JSON診断、単体・ブラウザ・ビルドテスト、性能計測、依存ライセンス通知、静的サイトとGitHub Pages。
- **SDK:** `@simpludify/core@0.1.7` と `@simpludify/web@0.1.7` はnpmで公開済みです。[npm導入ガイド](npm.md)。

## 現在の制約・未実装事項

- 高度な剛体物理（衝撃・角速度・摩擦・Joint）、CCD、複数Camera/Viewport、無限Map、Save/Load、Networking、Asset Manifest、GUIエディタは未実装です。
- Actor/Componentは削除時に破棄されます。Poolingはゲーム側で管理します。Scene再活性化は保持設定で有効になります。画像読み込みはゲームロジックと独立して失敗する場合があります。
- 地形衝突はCell接触、Solid/Trigger、必要に応じた16×16チャンク候補探索に対応していますが、斜面や一般多角形の物理応答は対象外です。
- タイル幾何は正方形・三角形・六角形（2方向）、セル特定、近傍・距離、色付きポリゴン表示に対応します。多角形Collider、画像UV/マスク、一般地形物理は未対応です。
- Web描画とCanvas UIの自動テストは主としてChromiumです。Safari/Firefox、実機のタッチ・IME・スクリーンリーダー、各種GPU、WebGLコンテキスト復旧の網羅的な検証は未完了です。
- ネイティブなWindows/macOS/Linux配布、Electron/Tauri、Android/iOSの正式対応は未実装・未検証です。ESM SDKの公開とWebでの動作を、ネイティブ配布済みという意味に解釈しないでください。
