# 設計思想とアーキテクチャ

Simpludifyは、同期的なDOM非依存シミュレーションと、非同期の準備・描画・入力イベント・DOM UIを所有するブラウザホストを明確に分離します。実験的なSDKワークスペースは`@simpludify/core`と`@simpludify/web`です。Electron、AIサービス、汎用ECSスケジューラなどはCoreに含まれません。最小の行数や最大の機能数を目標にせず、理解しやすく、一貫していて、柔軟で保守しやすいAPIを優先します。

## 責務と境界

| 概念              | 責務                                                                                                | 所有権                                                      |
| ----------------- | --------------------------------------------------------------------------------------------------- | ----------------------------------------------------------- |
| Engine            | アクティブなScene、固定されたフレーム入力、明示的ステップ実行、seed付き乱数、診断／スナップショット | 1つの現在のScene                                            |
| Scene             | 同期ライフサイクル、Actor所属管理、更新コールバック、ローカルイベント、シミュレーションタイマー     | Actorsおよび登録されたクリーンアップ                        |
| Actor             | 識別、所属状態、有効フラグ、Component合成                                                           | Componentsおよび登録されたクリーンアップ                    |
| Component         | 1つの再利用可能な振る舞いまたはデータ機能                                                           | 1つのActor。自身の購読およびクリーンアップ                  |
| EventBus          | 任意の型付き同期通知                                                                                | 明示的なバス所有者。任意の購読所有者                        |
| Camera / 座標関数 | ワールドからスクリーンへの投影およびその逆変換                                                      | 純粋なCoreデータ。描画やDOMの知識を持たない                 |
| Grid              | 固定サイズの高密度整数インデックス2次元データおよび矩形走査                                         | プレーンな値／参照。Scene所有権や自動破棄を持たない         |
| Web Game          | Scene factory管理、非同期セットアップ／描画準備、フレーム駆動／リサイズ／入力サービス               | Engine、Renderer、UI、ホスト要素                            |
| PixiRenderer      | Sceneのプレゼンテーションおよび動的なRenderableの整合                                               | Containers、DisplayObjects、画像Texture、保留中の画像ロード |
| DOM UI            | ネイティブなラベル／ボタン／パネルのレイアウト、フォーカス、選択的なテキスト更新                    | 1つのマウントされたSceneオーバーレイ                        |

Coreのコンパイルは、DOMやNodeの環境型（ambient types）を含まないES2022ライブラリを使用します。境界バリデータは外部からのCoreインポートおよびCore/WebにおけるElectron依存を拒否します。Coreの描画契約はキャラクターリストやプラットフォームオブジェクトではなく、Sceneと座標変換を受け取ります。

## Sceneのライフサイクル

Sceneは構築およびアプリケーション設定を網羅する**Preparing**から開始します。その同期状態は以下の通りです。

| 状態      | 意味                                                       | 正当な遷移先       |
| --------- | ---------------------------------------------------------- | ------------------ |
| Preparing | Actor/Component/リソースを設定可能。更新は行われない       | Ready, Disposed    |
| Ready     | 呼び出し側が準備完了を宣言。更新は行われない               | Active, Disposed   |
| Active    | Engineのステップ実行に適格                                 | Inactive, Disposed |
| Inactive  | 非アクティブ化フックが実行中。新しいリソースや再利用は不可 | Disposed           |
| Disposed  | 終端状態。所有リソースは解放済み                           | なし               |

`Scene.markReady()`は同期的な準備完了宣言です。Coreはアセットを読み込まず、ブラウザのPromiseをawaitすることもありません。WebのfactoryはmarkReadyやEngine.activateの呼び出しをホスト側に委ねます。`Engine.activate`はヘッドレスでの利便性のためPreparing状態のSceneを受け入れてReadyを宣言できますが、ブラウザコードは非同期準備が成功した後にのみmarkReadyを呼び出します。Engineの初期既定Sceneは、明示的なアクティブ化または最初のヘッドレスstepまでPreparingのままです。初期の既定アクティブ化はすでに注入された入力を保持し、Sceneの差し替えは入力をクリアします。

EngineはSceneを排他的に要求します。アクティブな同一インスタンスに対するアクティブ化はno-opです。差し替えにより旧インスタンスは非アクティブ化され破棄されます。非アクティブまたは破棄されたインスタンスが再アクティブ化されたりプールされたりすることはありません。Webのfactoryは、現在のIDの再リロードであっても、完了したリロードごとに新しいインスタンスを作成します。アクティブ化の前にアクティブ化フックを登録してください。これらはロジック用フックであり、マウントされたUIレイアウトを問い合わせる前にWebのrun/changeSceneをawaitしてください。

コミット前は、不正な状態や所有権エラーが発生しても現在のSceneは変更されません。コミット時、Engineは新しいアクティブSceneをインストールし、次に旧Sceneの非アクティブ化、旧Sceneの破棄、新Sceneのアクティブ化コールバックを実行します。一部のコールバックが失敗しても、すべてのライフサイクルクリーンアップコールバックが実行されます。コールバックの失敗はコミット後に集約され、新しいSceneはアクティブなまま維持されます。不完全に適用された遷移を防ぐため、同期的にネストされたEngineのアクティブ化やステップ実行は拒否されます。

アクティブなSceneの直接破棄は終端処理であり、暗黙の画面遷移ではありません。その後のEngine stepは、別のSceneがアクティブ化されるまで拒否されます。WebアプリケーションではGameを通じてナビゲーションを行い、GameがプレゼンテーションとCoreを協調して管理します。

## Web Sceneトランザクション

1. `Game.run`はレンダラーを初期化し、初期アセット、Coreのアクティブ化、UIのアタッチ、初描画が完了した後に単一の起動Promiseを解決します。繰り返しの呼び出しはこれを共有します。ナビゲーションには起動のawaitが必要です。
2. `changeScene(id)`は要求を直列化します。直近の保留中IDと同じ連続リクエストはPromiseを共有し、重複したリロードをキューに入れません。完了後または別のIDを挟んだ場合は同一IDであっても新しいインスタンスを作成します。失敗した要求がキューを汚染することはありません。
3. ステージされたSceneとそのAbortSignalはトランザクションに属します。ユーザーのセットアップは非同期にできます。古いアクティブSceneは待機中も更新を継続します。
4. PixiはステージされたSceneを準備し、初期の視覚リソースを解決します。DOM UIはDOMツリーから切り離された状態で構築されます。準備が失敗した場合、候補Sceneは破棄され、そのsignalはアボートされ、古いアクティブSceneと表示はそのまま維持されます。
5. Coreが同期的アクティブ化をコミットします。その後Webが対応するプレゼンテーションとオーバーレイをインストールします。古い視覚・UIのクリーンアップは冪等であり、古いSceneの破棄に連動します。コミットされた新しいSceneを保持したまま、ライフサイクルコールバックのエラーが報告されます。
6. Gameの破棄は、ユーザーセットアップが決して解決しない場合であっても、アクティブまたはキューにあるナビゲーションを速やかに拒否します。Sceneのsignalをアボートし、ステージ中／現在のSceneを破棄し、1本のフレームチェーンをキャンセルし、入力／リサイズリスナーおよび所有DOMを除去し、レンダラーを破棄します。遅れて準備されたリソースは直ちに破棄されます。ユーザー独自のPromiseを強制停止することはできません。提供されたsignalを使用し、awaitの前にクリーンアップを登録してください。

アクティブ化フックによって作成されたActorは実行時追加です。アクティブ化後にそれらの画像を待機するにはwhenReadyを使用してください。コミット後のレンダラー／描画失敗は実行時エラーであり、ロールバックの保証ではありません。更新中の例外は、すでに変更された状態を巻き戻すことなく、そのstepの残りの処理を中断します。ヘッドレス呼び出し側がエラーを処理できるよう、Coreはその再入ガードをクリアします。バックグラウンドの更新／描画例外は診断オブザーバーに届き、Web Gameを停止／破棄します。

起動後の `onActivate` は次のScene遷移をキューに追加できます。返されたPromiseは同期フックの外で処理してください。コミット済みのSceneの表示取り付けや初回描画に失敗した場合、遷移のPromiseをrejectし、Gameを破棄します。

## ActorとComponentの所有権

ActorはDetached、単一のSceneにAttached、または終端のDisposedのいずれかの状態を取ります。明示的なIDはScene内で一意でなければなりません。省略されたIDはSceneによって決定論的に割り当てられます（`actor-1`など）。Actorの除去はそのActorを破棄します。転送やプーリングは暗黙には行われません。除去後に明示的なIDを再利用できますが、生成されるIDはScene内で単調増加します。

Componentは単一のActorにアタッチされ、破棄後に再利用することはできません。`Actor.add`は依存関係が先に追加されていることを要求します。依存関係の要件は構造的な存在制約であり、一般的なスケジューラや自動factoryではありません。不足・重複・循環依存・インスタンス共有・必須依存コンポーネントの先行除去は診断されます。アタッチの失敗が孤立した依存側を残さずにロールバックできるよう、`onAttach`内からの構造的なadd/remove呼び出しは拒否されます。`onAttach`は依存関係を読み取り、リソースを登録できます。Actorはアタッチの逆順でComponentを破棄し、依存先を先に追加する規則に従って依存側を依存先より先に破棄します。依存側のクリーンアップ／onDestroyの間、依存関係は読み取り可能なまま維持されます。各Componentは破棄後に検索ロスターから除去されます。

TransformとRenderableは受動的なデータです。Motionは移動を所有し、必須のTransformをキャッシュします。ActionMovementはUpdate中に明示的に注入されたAxis2D ActionReaderとscaleをMotion.directionに適用します。Motionはコマンドを生成するUpdate Componentの後のIntegrate中に、direction × mutable speedを積分します。CharacterはこれらのComponentを持つ合成プリセットであり、Engine自身がCharacterをインポートしたり更新したりすることはありません。カスタムComponentは完全に非表示にすることもできます。

Actorのenabledフラグはすべての更新と可視性をゲートします。Componentのenabledフラグは自身の更新をゲートし、Renderable.enabledはさらに視覚表示をゲートします。受動的なTransformの無効化は依存する振る舞いを無効化しません。ActionMovementは無効化または除去されたときに自身のdirectionをクリアします。構造的な依存関係は無効化されていても利用可能です。

## 更新の一貫性

各Engine stepは次の順序で実行されます。

1. deltaを検証し、必要に応じて初期アクティブ化を完了する。収集されたデバイス／論理入力から、Actor/Component/タイマーの適格性とアクティブなすべての論理Actionフレームを捕捉する。
2. 一時停止中であっても、論理onPressedコントロールを配信する。新しいActor/Component/タイマーは次のstepを待ち、書き込みは次の入力境界に反映される。
3. 捕捉されたすべてのActorについて、Scene追加順およびComponent追加順でInputフェーズComponentを実行する。
4. 同一順序でUpdateフェーズComponentを実行する。カスタム移動ポリシーやActionMovementはここでコマンドを計算する。
5. Integrate Component（Motionを含む）を実行し、次に位置のクランプ・発射処理・衝突前の画面外クリーンアップのためにLateUpdate Componentを実行する。
6. 任意のScene所有CollisionWorldを含む、登録されたポスト更新フックを実行する。
7. 捕捉されたシミュレーションTweenを進め、次にアクティブSceneのシミュレーションタイマーとScene更新コールバックを実行する。
8. ホストへ戻り、変更された描画構造を整合して現在の状態を描画する。

メンバーシップやComponentの変更は検索APIから即座に可視化されます。新しいActorと新しいComponentは**次のstep**から更新を開始します。ActorやComponentの除去／無効化は後続の実行を直ちに抑止します。step開始時に無効化されていたActorは、step途中で有効化されても次のstepまで不適格のままです。変更によって反復走査が無効化されたり二重更新が発生したりすることはありません。システムグラフやアーキタイプストレージはありません。同フェーズ内の依存要件によってピアの順序が入れ替わることはありません。Motionごとに1つのdirection書き込み者を使用してください。2つの書き込み者が互いに上書きし合うのではなく、ActionMovementをカスタムUpdate Componentに置き換えることを推奨します。Inputフェーズのscaleポリシーは標準のUpdateアダプターより先行します。[移動契約](./specs/movement.md)でフェーズの移行と所有権を解説しています。

一時停止（Pause）は後続のシミュレーションフェーズ（衝突・タイマーを含む）を中断しますが、論理Actionの捕捉／onPressedコントロール、Webのプレゼンテーション、DOMコントロールは継続します。入力コールバック内でのresumeはそのstepのdeltaを使ったシミュレーションを許可し、Componentからのpauseは次のstepで有効になります。状態の変更は入力をクリアし、Webはタイムスタンプをリセットします。Sceneのナビゲーションは利用可能なままであり、Sceneは適切なタイミングで明示的に再開します。

InputSystemはキーボード／マウスデバイスの入力寄与とEngineの入力境界を所有します。KeyboardSourceとMouseSourceはデバイス状態のみを表し、方向や生のゲームフレーム、暗黙のスクリプト書き込み者は持ちません。ActionControllerが割り当てを解決し、キー入力と論理ActionSourceを結合します。論理的な保持値、保留Buttonエッジ、キャプチャされたActionフレームを所有するのはActionControllerのみです。移動Componentが生の物理キーを読み取ることはありません。ActionReaderは読み取り専用で型付けされたScene依存関係をComponentに明示的に注入し、ActionMovementはSceneを跨ぐ参照を拒否します。[統合入力契約](./specs/action-input.md)を参照してください。

`Engine.step`は上限がなく、固定された制御入力、ステップ数、seed、ユーザーコードに対して決定論的です。Webは既定で0.05秒の上限を持つ可変RAF deltaを使用し、過剰な停滞時間を破棄し、非表示時にキーをクリアし、再開時にタイムスタンプをリセットします。外部の時間や乱数、非同期アセットの完了順序、GPUの出力は決定論的保証ではありません。

## 接触判定と位置補正

Colliderは幾何形状、layer/maskフィルタ、明示的なTrigger/Solid応答ポリシーを所有します。CollisionBodyは静的／動的補正の重みと質量を個別に所有し、速度の積分は所有しません。MotionはTransformへ意図を積分し、任意のScene所有CollisionWorldがその後に位置を補正します。Bodyを持たないSolidは固定されます。既存のColliderの既定値はTriggerのままです。

円と回転矩形のナローフェーズは最小移動法線とめり込み深さを返します。これはcollision-geometryに配置され、collision-responseは重み付けされた移動のみを含みます。CollisionWorldは所有権、ブロードフェーズのスイープ、決定論的なペア追跡と通知を保持します。すべての適格な幾何形状は最初の補正前に検証され、ペアごとの幾何形状は有界な順次補正中に更新されます。補正によって生じた新たな重なりは繰り返しのスキャンで発見されます。最終スキャンで補正後位置におけるTrigger接触を捕捉し、Solid接触は応答反復中の遭遇を保持します。この後に初めて、シミュレーションTweenやタイマー／Scene.onUpdateの前に接触イベントが配信されます。

除去や無効化は後続の配信を抑止し、破棄された受信者には何も届かず、Sceneやワールドの破棄は合成Exitなしに静かにクリアします。位置補正はコールバックの前にコミットされます。コールバックの失敗によって位置がロールバックされることはありません。有界な反復回数ですべての密集や狭い隙間を解決できるわけではありません。これは位置の押し戻しであり、力・力積・角運動の物理シミュレータではありません。離散的なすり抜けの可能性は残ります。[API契約](api.md#triggerとsolidの接触)を参照してください。

X軸スイープが保持されているのは、測定されたコストからより複雑な空間インデックスの導入が正当化されていないためです。密集した重なりや不利な軸分布では二次的なコストになります。Triggerのみのワールドでは応答反復は実行されません。

CameraFollowはホストから独立したワールド空間ヘルパーであり、zoomを考慮した境界と任意の指数平滑化を備えています。アプリケーションは通常Scene.onUpdateから位置補正後にこれを呼び出します。描画やSceneへの依存、特別なEngineの挙動は追加しません。

## イベント・タイマー・クリーンアップ

イベントはデバッグ名から独立した同一性を持つ任意の型付きトークンです。配信は同期的で登録順です。ディスパッチはリスナーをスナップショットします。追加は次回のディスパッチを待ち、購読解除や破棄は即座に有効になります。異なるイベントは深さ優先でネストできますが、同一バス上での同一トークンの再帰的emitは拒否されます。エラーが発生しても適格なすべてのハンドラが実行され、失敗は集約されてエミッターに再スローされます。Promiseを返すハンドラは`EVENT_ASYNC_HANDLER`で診断され、未処理のrejectionを防ぐためにrejectionは消費され、配信は継続します。非同期タスクはハンドラの外側で明示的に管理しなければなりません。

Scene/Actor/Componentのローカルバスは遅延割り当てされます。ローカルバスの破棄によりすべてのリスナーが除去されます。外部バスの購読ではScene/Actor/Componentを所有者として指定でき、手動での購読解除は所有権コールバックも除去します。グローバルなルーティングを必要とするユースケースが存在しないため、グローバルなGameバスは存在しません。アプリケーションは明示的にEventBusやLifetimeを所有できます。

`Scene.after/every`はシミュレーション秒を使用し、ホストタイマーを使用しません。これらは所属するSceneがステップ実行されるときにのみ動作します。繰り返しタイマーは1stepにつき最大1回配信され、飛び越えた反復を破棄し、端数のインターバル残余を保持します。0秒のワンショットは次のstepで発火します。タイマーの適格性は論理ActionコールバックおよびすべてのScene更新フェーズの前に捕捉されます。更新、接触、タイマー、Sceneコールバック中に追加されたタイマーは次のstepを待ちます。ActorやComponentの破棄によってタイマーを自動キャンセルできますが、enable/disableはタイマーを一時停止しません。タイマーハンドラの失敗は、他の期日を迎えたコールバックが実行された後に集約されます。

破棄（Disposal）は冪等です。一部が失敗しても登録されたすべてのクリーンアップが実行されます。Sceneの破棄は両方のTweenクロック、タイマー、イベントバスをキャンセルし、ActorとComponentを破棄し、次に登録の逆順でSceneのクリーンアップを実行します。Actorは所有クリーンアップを実行し、バスを閉じ、アタッチの逆順でComponentを破棄します。Componentは所有購読とバスを解放し、onDestroyを呼び出します。クリーンアップ登録が返す関数は登録解除関数であり、クリーンアップ自体を実行するものではありません。

## 座標・カメラ・Viewport・DPI

`WorldPoint`はゲーム単位の座標です。`ScreenPoint`はホストローカルのCSSピクセル座標です。`Viewport`はそのホスト内のオフセット矩形です。`LogicalResolution`は公称の表示範囲（既定800×450）であり、Canvasのバッキングピクセルとは独立しています。`PhysicalPoint`はDPRでスケーリングされたスクリーン座標であり、物理ピクセルはレンダラーが所有します。

Cameraのx/yは公称可視範囲のワールド左上座標を指定し、zoomはその範囲の中心を基準とします。既定のCamera(0,0,1)は元の表示を再現します。Fitは中央揃えの黒帯を伴い、Viewportと論理サイズの小さい方のスケールを使用します。Fillは大きい方のスケールを使用してクロップします。AdaptiveはViewportのCSS寸法を論理範囲として使用します。zoomはクリップ矩形を動かさずにスケールを乗算します。DOM UIはホスト全体にリフローし、Cameraやワールドのアスペクト比の影響を受けません。

純粋なcreateViewTransform/worldToScreen/screenToWorld関数が可逆なマッピングを提供します。`Game.pointerToWorld`はクライアント座標をホストローカルのスクリーン座標に変換した後に逆変換を適用し、ホストのバウンディングボックスのスケーリングを考慮します。外部の点も変換可能ですが、必要に応じて`containsScreenPoint`で可視境界内かを確認してください。

Webレンダラーは既定で`min(devicePixelRatio, 2)`を使用し、pixelRatioで設定可能です。比率の変化を検知し、論理解像度やCameraから独立してバッキングバッファをリサイズします。

## プレゼンテーションリソース

Pixiのプレゼンテーションは、Sceneの構造リビジョン変更時に構成員を整合します。各Renderableは表示状態と変更不可なsource記述のための独立した検証済みリビジョンを持ちます。Transform、enabled、visibility、opacity、depthは描画ごとに読み取られ、関連する変更のみが順序を再構築します。等しい深度ではActor追加順が保持されます。図形幾何や塗りの変更は既存Graphicsを再描画し、画像の差し替えはSpriteを再利用し、変更のない幾何形状は再構築されません。色合いやレイアウトの変更で画像が再ロードされることはありません。

Visualは要求されたsource/generation、コミットされた表示、独立して取得された画像リースを区別します。保留中の差し替えは以前の画像や図形を保持します。不要になった要求はキャンセルされ、世代・現在ソース・ライフサイクルの検査により遅れて届いた結果は拒否されます。実行時エラーが発生しても論理更新を停止することなく古い表示が維持されます。準備完了は同期された最新の要求に追従し、無関係なロードを待たずに現在のエラーをrejectし、除去や破棄で待機を解除します。失敗したステージング準備は候補を破棄し、アクティブSceneを維持します。[動的描画](./specs/rendering.md)を参照してください。

ActorやComponentの破棄は保留中の利用をキャンセルし、表示／画像リースを解放します。Rendererローカルの生きた参照キャッシュが、解決された画像URLをVisual間および重複するSceneプレゼンテーション間で結合します。各コンシューマは冪等なリースを持ち、最後の解放のみが保留ロードを中断するか共有Texture/TextureSourceを破棄します。画像はPixiのグローバルキャッシュをバイパスします。診断機能はVisual数、保留中／コミット済みの参照数、一意のエントリ／ロード数、所有Textureオブジェクト数を区別して報告します。

DOM UIは引き続きネイティブのFlexbox/Grid、textContent、フォーカス可能なボタン、選択的なラベル購読を使用します。オーバーレイは空の領域でpointer-eventsが無効化されており、可視のコントロールやパネルのみが参加します。Canvas UIはCoreモデルと有界なFlexサブセットを使用し、実行時レイアウト依存関係や必須エディタは導入されません。

## 公式サイトと将来の通信

公式サイトはエンジン依存ではなくビルドツールです。既存のViteとビルド時Markdown変換により、静的ページと独立してビルドされたサンプルドキュメントを出力します。サンプルのブートストラップはCoreの外側でpagehide/disposalと起動診断を所有します。日本語と英語の利用者向けガイドは対応するルートを持ちます。APIやライフサイクルの契約は内部の実装・性能記録と区別されます。

コード主導とは、最も短い構文ではなく、一貫性があり、理解しやすく、保守しやすい構成を意味します。高水準な既定値と低水準なアクセスが共存し、型付きイベントは任意のままです。Blockfallは物理Colliderではなく通常のゲームロジックでグリッドルールを表現しています。Prism RaidはTriangleビジュアルの下で円形Triggerを使用し、敵のパターン、発射、ダメージ、ウェーブはゲーム所有のComponentと状態のままです。ゲームの操作感が許す限り円や箱の近似で十分であり、厳密な輪郭一致は要件ではありません。

静的配信はネットワーク機能とは無関係です。スタンドアロンのサンプルは配信後に外部ゲームサービスを必要としません。将来の通信方式、シミュレーションの実行場所、状態の権威は別個の決定事項でなければなりません。P2P、プレイヤーホスト、専用サーバーの設計は将来候補であり、実装済みAPIではありません。DOM非依存シミュレーションは特定の通信方式に縛られることなく再利用可能であり続けます。

## 制御された実行（Replay・固定ステップ）

Engineは独立したRandomManagerを所有します。厳密な名前付きストリームが検索順序から独立してseedを導出し、Sceneの差し替えは消費状態を維持し、Engineの破棄はすべてのハンドルを閉じます。ランダムスナップショットはseed／状態／呼び出し回数を検査し、任意のゲーム状態を復元するものではありません。

ReplayRecorder/ReplayPlayerは1つの任意の実行ドライバをアタッチします。ドライバがない場合、Engineはリプレイフレームやランダムスナップショットを捕捉しません。キャプチャはすべてのActionフレームが凍結された後、かつ任意の入力コールバックの前に発生し、Buttonの遷移と一時停止コントロールを保持します。再生はその同一境界で検証済みの論理フレームを供給し、生の入力を除外します。コントローラーIDによって重複するAction名を明確化します。初期サポートは新しいEngineと単一のSceneを前提とし、サポート外の遷移はコミット前に拒否されます。データの永続化はCoreの外側に保たれます。

FixedStepRunnerは小さなホスト時間アキュムレータです。Webは可変RAFステップを維持しつつこれを選択できます。リプレイのペーシングは記録されたdeltaを有界な処理量で消費し、記録されたstepを決して破棄しません。どちらのヘルパーも普遍的な決定論、補間、またはセーブステートシステムではありません。[乱数・Replayの契約](./specs/replay.md)を参照してください。

## Spriteフレームと再生

SpriteSheetには変更不可な画像／フレームメタデータのみが含まれます。SpriteAnimationはクリップ定義をコピーし、LateUpdateで1つのActor再生カーソルを所有します。再生中はRenderable.sourceを書き込み、他の外観プロパティを保持します。Webはデコードされた画像境界を解決し、既存のSharedImagesエントリ内に切り抜きTextureビューをキャッシュします。最後の画像リースは、共有ベースソースを解放する前にこれらのビューを破棄します。[Sprite契約](./specs/sprites.md)を参照してください。

## Tilemap配置

`Tilemap.place(scene)`は内部Actorと受動的なTilemapLayerを使用して所有権を再利用し、独立した`map.get(x,y)` APIを保持します。データはコピーされた非公開Gridです。プレゼンテーションはセルの無効化を購読し、既存の寿命と共に購読とリソースを除去します。専用のtilemap-visualモジュールは可視セルのSpriteとシートリースのみを所有します。描画グループはRenderable順序を共有し、逆ViewTransform.clipがカリングを供給します。任意の[Tilemap衝突](./specs/tilemap-collision.md)は同期的なCoreデータであり、既存のCollisionWorldによって問い合わせられます。Actorとタイルのペアはポリシー、フィルタ、ナローフェーズ、応答、観測、順序付けされた配信、および寿命機構を共有します。

## Canvas UIのホスト統合

Canvas UIはCoreが所有する論理ツリーであり、ActorやComponentではありません。Sceneまたは単純なLifetimeがその同期状態を所有します。GameはDOM UIおよび視覚準備と並行して1つのルートをステージングし、Pixiプレゼンテーションはコミット時にワールドの上にマウントされます。CoreのPointerRoutingインスタンスがジェスチャーを所有します。1つのDOMキャプチャフェーズアダプターがブラウザ入力を供給し、ScenePointerワールドバスとCanvasノードバスを提供します。Downによって受信者が固定され、無効化されたジェスチャーIDは物理的な解放まで抑制されたままになります。独立したActionSourceが標準的な論理ゲームプレイパスのままです。ネイティブボタンミラーがポインターディスパッチを重複させることなくフォーカスとキーボードセマンティクスを提供します。[Canvas契約](./specs/canvas-ui.md)を参照してください。

## Coreモジュールと追加ホスト

[CoreモジュールとHost境界](host-boundary.md)で、検査済みの内部依存関係、移植可能なUI状態／レイアウト／入力フロー、キャンセル移行、レンダラー／Host／ターゲットの区別、具体的なHost実装手順を説明しています。[作業記録](../work-reports/README.md)で実装と検証のチェックポイントを保持しています。

Canvas Checkbox/Sliderは、既存UIツリー内の小さな任意のコントロールポートと型付き値ノード基盤を使用します。Coreは即時値、通知、範囲検証、フォーカス、ポインター調停を所有し、Webは描画、フォントメトリクス、ネイティブARIAミラーを所有します。Select/TextInput/NumberInputは世代検査付きネイティブセッションと分離された受け入れ値／ドラフトで値基盤を再利用します。Webはネイティブポップアップ／キャレット／選択／クリップボード／変換プレゼンテーションを所有し、アイドル時のテキストとコントロール背景はCanvas描画のままです。[Canvasコントロール](./specs/canvas-controls.md)および[ネイティブ文字編集契約](./specs/text-input-design.md)を参照してください。

## 数値アニメーションクロック（Tween）

汎用Tween/Easingはfoundationに配置され、診断機能とLifetimeにのみ依存します。Sceneは遅延初期化されるシミュレーションおよびプレゼンテーションスケジューラを所有します。シミュレーション適格性は入力の前に捕捉され、接触の後、タイマーの前に進みます。WebはEngineの一時停止中であっても、可視の上限付きフレームごとに1回表示秒数を供給します。リサイズやレイアウトによって時間が進むことはありません。表示時間は固定／リプレイシミュレーションから独立しています。ActorアダプターはRenderable専用の機能を付与し、UIアダプターは投影された平行移動／透明度、またはSlider値／表示機能を付与します。標準的なターゲット／キーチャネルがクロックを跨いで競合を管理し、同期的な寿命／無効化クリーンアップがコールバックに先行します。[Tween契約](./specs/tween.md)を参照してください。

## 多角形タイリング（TileGeometry）

[TileGeometry](./specs/tile-geometry.md)は、ストレージや所有権を持たずに不変のローカルタイリングを計算します。GeometryTilemapはGridカラーデータをコピーして1つの受動的Actor/Componentを配置し、Sceneの寿命とレンダラーの深度順序を再利用します。そのWeb Graphicsプレゼンテーションは変更されたインデックスを購読し、可視セルのみを保持します。既存のテクスチャTilemapおよび任意の衝突インデックスは分離されたままです。

Webの`Game.bindViewport(ui, node)`連動は、解決済みの専用Canvasレイアウトスロットをワールド投影に接続します。Gameはワールド描画およびポインター変換の前にUI幾何形状を読み取ります。CoreレイアウトはカメラやブラウザViewportの知識を持たないままです。UI単位はUI scaleを通じてホストCSSピクセルになり、DPRはプレゼンテーション専用のままです。このAPIはv0.1.2以降公開されています。

Web GamepadInputはDOM非依存のInputAdapterポートをInputSystemに登録します。ライブ入力境界ごとに、すべてのActionフレームを凍結する前にデバイスをサンプリングします。Replayはライブアダプターをスキップします。アダプターのリセットは既存の静的なpause/resume/Sceneクリアに参加し、個別のSourceゲートは通常の解放エッジを保持します。

## 仮想ポインターデバイス（v0.1.5公開）

ScenePointerは1つのVirtualInputターゲットプロバイダを所有できます。これはCanvas UIの後ろ、ワールドルーティングの前に移植可能なVirtualStick/VirtualButtonモデルを供給します。PointerRoutingが単一のキャプチャマップのままです。UIターゲットは既存のスクロール／コントロールセマンティクスを保持し、仮想ターゲットは解放／キャンセルまでDown時の同一性を維持します。モデルはコントローラー所有のActionSourceを使用し、既存のInputAdapterリセットポートを登録します。

有効化幾何形状はホストCSSピクセルのViewport空間で解決されます。組み込みの重なり検査と保守的なカスタム境界が、新しいレイアウトをコミットする前に同優先度の曖昧さを拒否します。Coreは値と経過プレゼンテーション時間を保持し、スクリーンスペースの描画状態を宣言します。Web Gameはレイアウト連動Viewportを解決し、プレゼンテーションクロックで保持を進め、Canvas UIの下にPixi仮想入力プレゼンテーションを所有します。

## 共通割り当てとキャプチャ（v0.1.6公開）

ActionControllerが設定および合成パスを保持します。任意のmouse/gamepadデータがActionBindingを拡張します。Webのゲームパッドソースはこれに従うか、明示的な従来の割り当てを保持します。既存のPointerRoutingがマウスジェスチャーを所有し、割り当てはワールドマスクのみを監視します。移植可能なInputCaptureがセッション状態、結果、寿命を所有します。Game所有のオブザーバーがキー／ボタンをニュートラル化し、パッドのポーリングを共有し、ライブアダプターをゲートします。[契約](./specs/input-bindings.md)を参照してください。
