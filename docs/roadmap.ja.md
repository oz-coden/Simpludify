# 実装状況と開発ロードマップ

[English](roadmap.md) | 日本語

Simpludifyは、コード主導・2D特化の実験的なTypeScript製ゲームエンジンです。この文書では、**実装済みの機能・今後優先する機能・意図的に対象外とする機能**を区別します。優先度は開発方針であり、公開日や将来のAPI名の確約ではありません。API、性能、移行手順、プラットフォーム対応は個別の設計とゲーム実装による検証を経て確定します。

## 製品方針・実装上の原則

- **コードを中心としたゲーム制作**を優先します。ゲーム側でロジックとUIを定義し、入力、描画、ライフサイクル、Host固有の処理をエンジンが扱います。標準的な用途でGUIエディタ、手書きのHTML、プラットフォーム別の実装を強制しません。
- **CoreとHostの責務を分離**します。CoreはHost非依存を維持し、音声・描画・ファイルI/O・ネットワーク・配布の環境依存処理は明示的なアダプターで扱います。プロセス間の毎フレーム通信など不必要な処理は避けます。
- 既存のAction、Scene、Actor/Component、Canvas UI、Tilemap、CollisionWorldを活用し、同じ責務を持つ別系統のフレームワークを増やしません。破壊的変更には移行方針が必要です。
- **小さく安定した構成要素**、適切な初期設定、必要な場合だけ利用する拡張口を重視します。大規模機能は実際のゲームで必要性を確認してから実装します。
- 重い物理演算、ネットワーク、デスクトップ・モバイルHostなどは、可能な限り**任意導入の独立モジュール**にします。基本ランタイムへ必須依存させません。
- 各機能にはAPI文書、所有権とエラー処理の定義、代表的なHeadless/ブラウザテスト、破棄テスト、既知の制約が必要です。実験的な動作確認と正式なプラットフォーム対応を混同しません。

## 今後のロードマップ

同一優先度でも必ずしも並行実装・順番固定ではありません。実装順序は依存関係と具体的なゲームでの必要性から決めます。

| 優先度 | 分野 | 目指す機能 | 主な設計・検証事項 |
| --- | --- | --- | --- |
| **高** | **Audio** | BGM・効果音、再生制御、音量・ミュート、カテゴリ/バス、ループ、フェード | ブラウザの自動再生制約、Host抽象化、Scene/Actor所有権、同時再生、解放 |
| **高** | **Save / Load** | 明示的なゲーム状態の保存・復元、バージョン付きデータ、検証・移行・失敗時の安全性 | ReplayやEngine Snapshotと区別し、保存先は差し替え可能にする |
| **高** | **Assets管理** | 画像・音声・フォントの共通読み込み、事前読み込み、参照管理、進捗とエラー、キャッシュ | 重複ロード、シーン間共有、中断、リソース解放、安全なURL |
| **高** | **Scene管理拡張** | Sceneを保持したままの移動、一時停止・再開、重ね合わせ、遷移ポリシー | 入力優先度、更新/描画停止、非同期準備、所有権、失敗時の復旧 |
| **高** | **再利用可能なCanvas UI** | モーダル、確認・通知ダイアログ、オーバーレイ、設定画面・メニュー部品 | フォーカストラップと復帰、キャンセル、アクセシビリティ、重なり |
| **高** | **Particle / Effects** | 軽量なエミッター、一般的な視覚効果、明示的な負荷と寿命の管理 | バッチ処理、プール、破棄、描画依存、シミュレーション時間との分離 |
| **高** | **Camera拡張** | 画面揺れ、遷移、追従・制限の改善、用途に応じた複数カメラ/Viewport | 座標変換、ポインター、UI配置、リサイズ、DPR、複数視点 |
| **高・段階的** | **Networking** | 任意導入の通信抽象化、セッション/メッセージ、後に同期方式を拡充 | サーバー/P2P、権威モデル、セキュリティ、順序、再接続、決定論の限界 |
| **中** | **高度な状態機械** | 型付き階層状態、遷移、ガード、アクション、ライフサイクル | Scene/Componentとの連携、非同期・時間依存遷移、テスト可能性 |
| **中・調査** | **物理演算拡張** | 現行Trigger/Solidを維持しつつ、重力・力・摩擦・反発・Joint等は外部2Dライブラリの採用を評価 | 任意導入のアダプター、座標・単位、衝突イベント、CCD、ライセンス |
| **延期** | **キーコンフィグUI・複合入力** | 将来的な再割り当て画面、複合キー、シーケンス、高度なキャプチャ | 既存Binding/Captureと競合ポリシーが成熟するまで導入しない |
| **延期** | **デスクトップ・モバイル配布** | Electron/Tauri、Android/iOSへの展開 | 権限・Sandbox、署名、入力/IME、実機テスト、サイズ・起動時間 |
| **再検討** | **仮想化リスト** | 大量のUI項目を効率的に描画・操作 | 実際の負荷、フォーカス、スクロール、識別子、アクセシビリティ |

### 高優先度の作業領域

#### Audio・Assets管理

- Web Audio APIをゲームコードから直接扱わずに済む、最小限の音声APIから始めます。再生ハンドル、全体/カテゴリ音量、ミュート、標準的な再生制御を提供する構想です。ブラウザの自動再生制約は明記します。
- 画像の既存ロード・共有・リース機構を活かして、事前読み込み、状態表示、エラー処理を段階的に統合します。フォント準備と音声デコードはHost固有の処理として整理します。
- アプリ全体とSceneのどちらがリソースを所有するかを明示し、シーンの重複稼働、読み込み失敗、中断、繰り返し利用、破棄を検証します。無制限の暗黙キャッシュは避けます。

#### Save / Load

- ゲーム側が保存対象と復元方法を明示する、バージョン付き保存形式を基本とします。あらゆるComponentの自動シリアライズや任意ステップ途中からの完全復元は約束しません。
- 論理状態のシリアライズと、ブラウザ・デスクトップ・モバイルでの保存先を分離します。破損データ、スキーマ検証、移行、書き込みの安全性を設計します。
- **Replayは同一条件から入力を再現する仕組みであり、Save / Loadではありません。** 複数Sceneと設定・Assetsを含む実例で保存・読み込みを検証します。

#### Scene保持・オーバーレイ・モーダル

- 破棄されずに保持されるSceneの停止・再開、タイマー、更新、背面描画、最終破棄の扱いを定義します。現在の破棄型ナビゲーションも残します。
- Sceneの重ね合わせ、最前面の入力所有権、キーボード・ゲームパッド、ワールドポインター、画面固定UI、非同期遷移失敗時の復旧を定義します。
- Canvas UIの既存部品の上に、確認/キャンセル結果を返すダイアログ、フォーカスの退避・復帰、ネスト表示などを実装します。DOMだけの別系統のモーダル機構は優先しません。
- この文書の名称は**構想上の名称**であり、まだ公開APIではありません。実ゲームでの利用例を検討してから確定します。

#### Particle・Camera・ゲーム進行支援

- Particleは定番のエフェクトと設定可能なEmitterから始め、Emitterごとの上限、コスト、寿命と破棄を管理します。大量の物理的なParticleと軽量な視覚演出は区別します。
- Cameraは追従、画面揺れ、演出用遷移を先に充実させます。複数Viewportは実際の要求に合わせて検討し、座標変換やUI/入力境界をテストします。
- Actor・敵AI・メニュー・ウェーブ制御に使える、任意導入の階層状態機械を検討します。遷移ガードとクリーンアップを定義し、敵やウェーブのサンプルで効果を確かめます。

#### Networking：段階的な任意導入

1. TransportとSessionのインターフェース、型付きメッセージ、切断とエラー処理を整備します。**サービスとしてのサーバー運営はエンジンに含めません**。
2. 実際のマルチプレイゲームで、状態複製、イベント/RPC、権威モデル、補間方式を選びます。万能な同期モデルを先に決めません。
3. 予測・Rollback・Lockstepは、決定論やReplayとの互換性が検証できてから検討します。固定ステップがあるだけでネットワーク決定論が保証されるわけではありません。
4. セキュリティ境界、利用者が付ける識別子、Hostの要件を文書化します。Coreは**完全オフラインで使用可能**なまま維持します。

### 物理演算・プラットフォームの拡張

- **Physics:** 現在の軽量なCollider/CollisionWorld（Trigger/Solid、位置補正）は維持します。高機能な剛体・Joint・CCDを要するゲームが現れたら、独立インストール可能な外部物理ライブラリを評価します。二重のソルバーで矛盾する衝突処理を起こさないよう、相互運用・所有権・移行を設計してから採用します。
- **Electron / Tauri:** Electron一択にはせず、両方を検討します。Webゲームコードを共通化し、Native Bridgeは最小限にし、適切なSandbox・権限制御・CSP等を導入します。両者固有のセキュリティモデルを別々に評価し、起動時間、メモリ、サイズ、終了時の後処理を比較します。
- **Mobile:** Host/配布対応に合わせてAndroidとiOSを調査します。タッチ、ソフトウェアキーボード、IME、アプリの一時停止、画面回転、性能、ストア配布要件を検証します。Webブラウザで動くだけではネイティブモバイル対応済みと見なしません。
- 別レンダラーやHostはできるだけCoreの定義を再利用し、必要なら独立モジュールとして提供します。

### 延期・任意・対象外

- **GUIエディタ:** 現在の開発対象外です。多数の今後のメジャー/マイナーリリースを経て需要が確認された場合にのみ再検討します（10リリース以上先というのは距離感の目安で、リリース予告ではありません）。コード主導が基本方針です。
- **組み込み3D:** 計画しません。2D専用の方向性を維持し、コミュニティが独立した3D拡張を試みることは妨げません。
- **高度なキーコンフィグ:** 複合キー、シーケンス、専用設定UI、高度なキャプチャは当面延期します。v0.1.6の物理Binding、単一入力Capture、JSON設定は維持します。
- **仮想化リスト:** 明確な性能上の要求が出るまで保留します。
- **完全なCSS/DOM互換、ECSへの必須全面移行、独自GPUレンダラー、多言語SDK、万能なマルチプレイ基盤:** 当面の製品目標ではありません。

### マイルストーンを決める際の受け入れ基準

1. 具体的なゲームで試せる最小の機能単位を選び、既存APIを可能な限り保ち、ライフサイクルと失敗時の挙動を先に決めます。
2. Coreの契約とHostのサービスを分離し、環境依存機能は必要に応じて任意アダプター化します。
3. 個別APIテストだけでなく、ゲームの一連の動作、Headless/ブラウザテスト、再利用・破棄・エラー処理を検証します。
4. 性能測定の環境と制約を記録し、対応を宣言するブラウザやプラットフォームごとに公開基準を設けます。
5. 実装・検証されたものだけを「実装済み」に移動し、計画と実績を常に区別します。

## 実装済み機能

以下は主にv0.1.6時点の機能です。機能ごとの正確な利用方法と制約はリンク先の英語技術資料を参照してください。

- **入力：** [物理Bindingと単一入力Capture](input-bindings.md)、キーボード・マウス・ゲームパッド設定、再割り当て、競合診断、JSON入出力。複合キーや標準キー設定UIは未実装。
- **仮想入力：** [仮想スティック・ボタン](virtual-input.md)（固定・浮動・追従）、有効範囲とPointer所有権、既存ActionSourceとの合成。
- **Tween：** [数値Tween](tween.md)、SceneのSimulation/Display Clock、順次・並列、Actor描画・UI値への適用、所有者による解放。
- **Canvas UI：** [Core側のUIツリーとFlex/テキスト/Pointerルーティング](canvas-ui.md)、フォーカス、ネイティブ編集、Checkbox/Slider/Select/TextInput/NumberInput。[スクロール](scrolling.md)はドラッグ、慣性、重なったスクロール領域、スクロールバーに対応。
- **Grid・Tilemap：** [固定サイズGrid](grid.md)、[有限Tilemap](tilemap.md)、レイヤー、SpriteSheetフレーム、カリング、セル編集、[任意の地形衝突](tilemap-collision.md)。
- **Sprite:** [SpriteSheetとSpriteAnimation](sprites.md)。グリッド・名前付き・矩形フレーム、画像共有、Actor単位の再生。
- **ゲーム基盤：** DOM非依存Engine、Sceneライフサイクル、Actor/Component、Transform/Renderable/Motion/ActionMovement、Character、型付きイベント、Simulation Timer、Seed付き乱数、Snapshot。
- **描画・Camera：** Pixiの図形・画像描画、描画順・透明度・表示制御、単一Camera/Viewport、World/Screen座標変換、CameraFollow、画像の非同期ロードとリース。
- **衝突：** 円・回転矩形のTrigger/Solid、レイヤー/マスク、Enter/Stay/Exit、CollisionBodyによる質量比に基づく位置補正。
- **シーン遷移：** 非同期準備、リクエストのキュー・統合、準備失敗時の旧シーン保持、破棄中のキャンセル。破棄しないSceneの保持・再開は未実装。
- **再現性：** [Random、Replay、固定ステップ](replay.md)。初期条件からAction列を再生できるが、任意時点でのSave/Loadや巻き戻しではありません。
- **サンプル：** Character、UI/Scene、Beacon Field、Signal Run、Blockfall、Prism Raid、Sprite Garden、Tile Trail、幾何タイル、Canvas UI、仮想入力など。
- **開発・配布：** dev/check/test/build/doctor CLI、JSON診断、単体・ブラウザ・ビルドテスト、性能計測、依存ライセンス通知、静的サイトとGitHub Pages。
- **SDK:** `@simpludify/core@0.1.6` と `@simpludify/web@0.1.6` はnpmで公開済みです。[公開記録](work-reports/2026-11-05-v0.1.6-publication.md)。

## 現在の制約・未実装事項

- 高度な剛体物理（衝撃・角速度・摩擦・Joint）、CCD、複数Camera/Viewport、無限Map、Audio、Save/Load、Networking、統一Asset Manifest/Font Manager、GUIエディタは未実装です。
- Actor/Componentは削除時に破棄されます。暗黙的なPoolingやScene再有効化はありません。画像読み込みはゲームロジックと独立して失敗する場合があります。
- [Tilemap衝突](tilemap-collision.md)はCell接触、Solid/Trigger、必要に応じた16×16チャンク候補探索に対応していますが、斜面や一般多角形の物理応答は対象外です。
- [タイル幾何](tile-geometry.md)は正方形・三角形・六角形（2方向）、セル特定、近傍・距離、色付きポリゴン表示に対応します。多角形Collider、画像UV/マスク、一般地形物理は未対応です。
- Web描画とCanvas UIの自動テストは主としてChromiumです。Safari/Firefox、実機のタッチ・IME・スクリーンリーダー、各種GPU、WebGLコンテキスト復旧の網羅的な検証は未完了です。
- ネイティブなWindows/macOS/Linux配布、Electron/Tauri、Android/iOSの正式対応は未実装・未検証です。ESM SDKの公開とWebでの動作を、ネイティブ配布済みという意味に解釈しないでください。

## 継続する品質・検証作業

1. 画像更新と破棄を含む長時間実行テストを強化し、ネイティブ/GPUメモリを追跡します。リサイズ・フォント更新の既知の負荷も測定します。
2. Chromium以外、物理デバイス、フォーカス・IME・タッチ・Gamepad再接続、WebGLのコンテキスト消失・復帰を検証します。
3. 新機能はSceneの切り替え、入力中断、アセット失敗、Pause/Resume、繰り返し生成・破棄、外部npm利用側ビルドで検証します。
4. Desktop対応時はHostごとのセキュリティと実行可能ファイルのスモークテストを整備します。ElectronではNode Integrationや権限を制限し、Tauriのセキュリティモデルも別途評価します。
5. 配布時にライセンス、起動時間、メモリ、圧縮サイズとインストール後サイズ、オフライン動作、プロセス終了後の後片付けを確認します。

GodotやPhaserとの性能優位性を主張する場合は、同じ負荷と制御された環境で測定し、バージョン・生データを保存する必要があります。既存の測定結果は特定環境における観測であり、一般的な優位性の保証ではありません。
